MongoDB · Solution architecture 04 / 11
The data model in play for the demo

Six collections. One document per household on the hot path.

profiles

Identity & relationship records across BT, EE, Plusnet. Carries the relationships[] graph (partner / guarantor / carer) and recorded consent for cross-brand linkage.

premises

UK UPRN-keyed addresses and line topology (ONT serial, exchange, FTTP vs FTTC, current line status). The household anchor every other document joins on.

interactions

The Service Hub: voice, webchat, mobile-app events. interactionSummary is auto-embedded by Atlas via Voyage AI — no app-side pipeline.

operations_wfm

Live field-service state: Openreach engineer dispatches, revised ETAs, delay reasons. Change-stream-driven so the agent sees the current status, not yesterday's snapshot.

orders

Provisioning, migration, hardware shipments. Carries DPD / courier exceptions so damaged-router cases surface on the pop before the caller mentions them.

customer_360 materialized

A pre-joined, read-optimised dossier per UPRN, maintained by MongoDB change streams. Single-key fetch at call-connect — sub-3 ms.

This demo uses synthetic data; the production solution would follow the same domain model, mapped to BT's existing Profile Hub, Service Hub and operational systems.

Core innovations

  • $rankFusion — one aggregation, two sub-pipelines (semantic + keyword), scoreDetails explains every hit to the agent.
  • Voyage AI auto-embedding (GA) — summaries embed on write, utterances embed on query. No app-side pipeline.
  • Progressive UI — caller + timeline + dossier appear in < 1 s; script streams token-by-token.
  • Grounded output — schema-validated briefing; every claim cites a specific interaction / order / work-order ID.
  • Closed loop — the current call writes back as a new interaction, auto-embedded, retrievable next time.

Roadmap  ·  one example path

Phased delivery. No rip-and-replace.

Illustrative  One example of how we would approach this challenge. The phasing and sequencing would be shaped by BT's own priorities, operational constraints and governance.

Phase 1 — Prototype validation

Sub-second multi-stage synthesis using Atlas, $rankFusion, voyage-4-large auto-embedding. Done today

Phase 2 — Premise Hub linking

UPRN keys across Profile Hub and Service Hub. Related-party links with recorded consent.

Phase 3 — Pilot agent assist

Predictive briefings on the highest-volume broadband queues. Post-call write-back closes the loop.

Phase 4 — Atlas-native materialization

Move the C360 materializer to Atlas Triggers / Stream Processing — zero new services for BT SRE to run.

Phase 5 — Convergence integration

Automated EE One eligibility rules for proactive cross-brand offers on live calls.

Phase 6 — Enterprise hardening

GDPR / consent framework, Queryable Encryption on phone numbers, OTel observability, SRE runbooks.
